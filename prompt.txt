EXISTING SYSTEM CONTEXT

There are two independent repositories:

- rule-engine:
  Java decision-table compilation and execution.
- rule-engine-expression-parser:
  Xtext expression language, validation, Java generation, and runtime helpers.

The system reads Excel decision tables:
- Yellow headers identify decision/input columns.
- Blue headers identify output/action columns.
- Exact fills, merged cells, match policy, blank rows, and output order affect semantics.
- The reported header colors are yellow FFFFFF00 and blue FF00B0F0.
- Verify detailed workbook behavior against current source and tests before presenting it as fact.

The active engine integration uses StatefulExpressionParser, not the older engine-local ExpressionParser.

At a high level, cell expressions are parsed and validated, Java expression fragments are generated, and the engine assembles generated rule classes. Those classes are compiled, loaded, and executed against request objects.

Explain two separate kinds of generation:
1. Xtext generates language infrastructure from the grammar during development/build.
2. The application generates Java rule code from grid expressions when preparing a grid.

Do not confuse these stages.

CUSTOM FUNCTION DESIGN ALREADY PRESENT

The current intended extension uses a plain Java FunctionRegistry:

- Functions are registered once when the application sets up its retained GridFactory.
- Registration is not repeated for each grid execution.
- Custom functions always require explicit arguments.
- The yellow-header field is not automatically supplied to custom functions.
- Existing built-in shorthand is handled separately.
- Registration can use reflection to inspect method metadata.
- Generated custom-function execution uses direct Java calls through generated typed wrapper methods.
- The previous FunctionRegistry.invoke execution fallback was removed.
- Functions that cannot support direct generated calls should fail with a useful diagnostic.
- An instance function's target object is retained and bound to the generated rule object.

FunctionCallBindings collects information while generating one Java class. Expression generation receives the same bindings object through a context map, conceptually:

    args.put(FunctionCallBindings.CONTEXT_KEY, bindings);

As expressions are generated, calls add information to that shared object. Later the engine uses its accumulated declarations and constructor initialization code, conceptually:

    sb.append(functionCalls.declarations());

Teach this with object references, a timeline, and a tiny generated Java example. Explain why constructing a new StringBuilder inside declarations() does not discard the information already stored in the bindings object.

Distinguish:
- Registration time.
- Parsing and validation time.
- Java generation time.
- Compilation time.
- Generated object construction.
- Rule execution time.

TYPED LIST OUTPUTS

The implementation also supports typed List results using an internal HelperFunctions.appendList helper.

Its intended behavior includes:
- Initializing a null destination.
- Appending a different returned list.
- Avoiding duplicate self-append when a function mutates and returns the same destination list.
- Requiring mutable existing destinations and compatible element types.

Teach these behaviors with object identity, aliasing, null handling, and tests when we reach list outputs.
